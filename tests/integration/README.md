# Контрактные тесты реального стенда

Тесты используют только HTTP и JSON. Они не импортируют Python-приложения, классы
хранилищ или обработчики событий. Полный сценарий проходит через восемь работающих
сервисов, PostgreSQL и RabbitMQ, включая Node.js и Go.

После запуска стенда:

```bash
RUN_HTTP_INTEGRATION=1 python -m pytest tests/integration -q
```

По умолчанию тесты отключены, чтобы обычный запуск unit/component-проверок не требовал
контейнеров. Для адресов по умолчанию используются `127.0.0.1:8001`–`:8008` в порядке
users, catalog, schedule, bookings, pricing, payments, sessions, notifications.
Каждый адрес можно переопределить через `USERS_URL`, `CATALOG_URL`, `SCHEDULE_URL`,
`BOOKINGS_URL`, `PRICING_URL`, `PAYMENTS_URL`, `SESSIONS_URL`, `NOTIFICATIONS_URL`.
Токен callback читается из `PROVIDER_TOKEN`, по умолчанию `demo-provider-token`.

Дополнительные настройки: `HTTP_TEST_STARTUP_TIMEOUT` (90 секунд),
`HTTP_TEST_WAIT_TIMEOUT` (45 секунд для событий), `HTTP_TEST_REQUEST_TIMEOUT` (20 секунд).
Стартовая проверка требует `status=ok` и `broker_connected=true` у всех восьми сервисов.

Проверяются:

- оформление, оплата, подтверждение, уведомление, отмена, освобождение интервала,
  отмена посещения/напоминания и результат возврата;
- неудачная оплата с последующим успехом, повторные callback и финальность успеха;
- поздняя оплата отменённой неоплаченной брони и возврат внутри обычного двухчасового окна;
- отсутствие автоматического возврата при отмене уже оплаченной брони менее чем за два часа;
- UUID, пагинация, обязательные/лишние поля, часовой пояс, шаг и длина интервала,
  строгие суммы, callback-токен и отсутствие частичного изменения при ошибке;
- одновременные удержания и оформления: один победитель, соседние интервалы разрешены;
- повтор удержания с тем же владельцем, семантически одинаковые `Z`/`+00:00`,
  проверка владельца и защита действующего интервала от изменения рабочего окна.

Каждая группа действий создаёт уникальные тестовые записи. Существующие данные не
сбрасываются и базы не очищаются; тестовые профили/столы остаются в стенде. Проверки
времени начала игры, десятиминутного истечения и 15-минутной неявки требуют управляемых
часов в unit-тестах. Здесь ранний старт/завершение проверяются по публичному API,
а ожидание игрового времени на несколько часов не выполняется.

## Проверка сохранения после перезапуска

Это отдельные две фазы одного теста. Он сам не управляет Docker/Podman и не делает
перезапуск без ведома запускающего. Между фазами нужно перезапустить приложения и
PostgreSQL с сохранением томов. Проверка `verify` только читает ранее созданные записи;
она не подменяет сохранённые данные вновь созданными.

```bash
RUN_HTTP_INTEGRATION=1 HTTP_PERSISTENCE_MODE=write \
  python -m pytest tests/integration/test_http_persistence.py -q -s

# Здесь перезапустить контейнеры, сохранив тома.

RUN_HTTP_INTEGRATION=1 HTTP_PERSISTENCE_MODE=verify \
  python -m pytest tests/integration/test_http_persistence.py -q -s
```

Файл контрольных ответов по умолчанию:
`/private/tmp/micro-polyglot-persistence.json`; другой путь задаётся
`HTTP_PERSISTENCE_FILE`. Снимок содержит по одному публичному объекту всех восьми
сервисов, включая подтверждённую занятость, тариф, оплату, посещение и отправленное
уведомление. Повторить проверку следует до начала тестового интервала (через 5–6 часов),
иначе законные таймеры могут изменить состояние посещения. Сам по себе запуск обеих
фаз без реального перезапуска не доказывает сохранение данных после рестарта.
