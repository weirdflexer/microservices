# Практическая работа 6. Синхронное HTTP API

## Цель и задание

Спроектировать HTTP API команд и запросов восьми микросервисов бронирования бильярда.
Описание содержит назначение операций, входные поля, ответы и ошибки. Синхронными
остаются операции, чей результат требуется до следующего шага; события оплаты,
подтверждения, отмены и посещения доставляются через RabbitMQ, как описано в работе 5.
Требование методички: каждый студент описывает минимум два своих микросервиса.

## Общие соглашения

Внешние адреса локального стенда:

| Сервис | Базовый URL | HTTP-операций |
|---|---|---:|
| S1 Пользователь | `http://localhost:8001` | 4 |
| S2 Каталог столов | `http://localhost:8002` | 4 |
| S3 Расписание | `http://localhost:8003` | 5 |
| S4 Бронирование | `http://localhost:8004` | 4 |
| S5 Тарифы | `http://localhost:8005` | 4 |
| S6 Платежи | `http://localhost:8006` | 4 |
| S7 Игровые сеансы | `http://localhost:8007` | 4 |
| S8 Уведомления | `http://localhost:8008` | 4 |

Пути ниже включают `/api`. Тела запросов и ответов — JSON UTF-8;
для тела передаётся `Content-Type: application/json`. Идентификаторы `*_id` — UUID-строки,
создаваемые владельцем сущности. В URL `{user_id}` и другие конструкции в фигурных
скобках заменяются фактическим UUID, фигурные скобки не отправляются.

Время задаётся строкой ISO 8601 **с часовым поясом**, например
`2030-01-15T12:00:00+03:00`; в ответе приводится к UTC. В query-параметре знак `+`
необходимо URL-кодировать как `%2B`, либо применять окончание `Z`. Рабочий интервал
использует полуоткрытый диапазон `[start_at, end_at)`, поэтому соседние интервалы
12:00–13:00 и 13:00–14:00 не пересекаются. Начало кратно 30 минутам; длительность
1–4 часа с шагом 30 минут. При создании предложения/брони начало должно быть в будущем.

Деньги: `amount` и `hourly_rate` — целые копейки; `100000` означает 1000 рублей.
Валюта только `RUB`. Дробные деньги и `float` не используются.

Списки возвращают JSON-массив объектов. `offset` — число пропускаемых элементов,
по умолчанию 0; `limit` — размер страницы от 1 до 100. Значение по умолчанию 50 для
S1/S2/S5 и 100 для S4/S6/S7/S8. Фильтры необязательны и применяются до пагинации.
Пагинация не создаёт стабильный снимок между запросами при одновременном изменении данных.

### Коды ответа и ошибки

| Код | Значение |
|---:|---|
| 200 | Успешное чтение, изменение или команда; ответ содержит итоговый объект |
| 201 | Создан пользователь, стол, тариф, предложение, удержание, бронь или уведомление |
| 401 | Неверный или отсутствующий `X-Provider-Token` у callback платежа/возврата |
| 404 | Запрошенная сущность не найдена, включая сущность, проверяемую через другой сервис |
| 409 | Конфликт состояния: занятое время, повтор контакта, истёкшее предложение, запрещённый переход |
| 422 | Неверный формат/тип/UUID, отсутствие обязательного поля, лишние поля, нарушение правил времени |
| 503 | Другой сервис недоступен или вернул серверную ошибку; время HTTP-ожидания ограничено |

Доменная ошибка: `{"detail":"Интервал уже занят"}`. У Python-сервисов ошибки
структуры FastAPI возвращаются как `{"detail":[...]}` с расположением поля и причиной;
Node.js и Go возвращают описание в поле `detail`. Во всех реализациях ошибки входных данных имеют код 422. Методы GET и
команды без тела не требуют `{}`. POST-команды с суффиксом `:cancel`, `:start`,
`:confirm` и т. п. соответствуют пользовательским операциям из методички.

В учебном стенде обычные бизнес-эндпоинты не требуют авторизации: `user_id` передаётся
явно, роли клиента/администратора не проверяются. Callback S6 требует заголовок
`X-Provider-Token`, равный `PROVIDER_TOKEN` (локально `demo-provider-token`). Это
договорённость учебного провайдера, не интеграция с реальным платёжным шлюзом.

## S1. Пользователь

| Метод и путь | Назначение | Запрос | Ответ |
|---|---|---|---|
| `POST /api/users` | Зарегистрировать клиента | `name`, `contact` | 201, `User` |
| `GET /api/users` | Получить клиентов | query `offset`, `limit` | 200, `User[]` |
| `GET /api/users/{user_id}` | Получить профиль и контакт | UUID пользователя в пути | 200, `User`; 404 |
| `PATCH /api/users/{user_id}` | Изменить профиль/контакт | хотя бы одно из `name`, `contact` | 200, `User`; 404/409/422 |

| Поле `User` | Тип и смысл |
|---|---|
| `id` | UUID клиента, возвращается сервером |
| `name` | Имя, 1–100 символов, пробелы по краям удаляются |
| `contact` | Email или телефон, 3–254 символа; уникален без учёта регистра |
| `created_at` | Время регистрации |

При создании обязательны `name`, `contact`. В PATCH не переданное поле сохраняется,
явный `null` и пустой объект запрещены. Дубликат контакта — 409. Проверка формата
телефона/email ограничена длиной; нормализация телефонов к международному виду не реализована.

```json
{"name":"Иван","contact":"ivan@example.test"}
```

Ответ содержит эти же поля и созданные `id`, `created_at`.

## S2. Каталог столов

| Метод и путь | Назначение | Запрос | Ответ |
|---|---|---|---|
| `POST /api/tables` | Добавить стол | `number`, `game_type`, необязательные `description`, `published` | 201, `Table`; 409 при повторе номера |
| `GET /api/tables` | Подобрать стол | query `offset`, `limit`, `published?`, `game_type?` | 200, `Table[]` |
| `GET /api/tables/{table_id}` | Получить сведения | UUID стола | 200, `Table`; 404 |
| `PATCH /api/tables/{table_id}` | Изменить карточку/публикацию | любое непустое подмножество изменяемых полей | 200, `Table`; 404/409/422 |

| Поле `Table` | Тип и смысл |
|---|---|
| `id` | UUID стола |
| `number` | Положительный уникальный номер в клубе |
| `game_type` | `pool`, `russian` или `snooker` |
| `description` | Текст до 1000 символов, по умолчанию пустая строка |
| `published` | Boolean, по умолчанию false; true разрешает бронирование |

Публикация — `PATCH` с `{"published":true}`. Занятость в карточке не хранится.
PATCH не принимает `null` и пустой объект. Фильтр `published=true` вернёт только
опубликованные столы; значение `game_type` имеет те же варианты, что и поле объекта.

## S3. Расписание

| Метод и путь | Назначение | Запрос | Ответ |
|---|---|---|---|
| `PUT /api/tables/{table_id}/schedule` | Задать рабочее окно | `opens_at`, `closes_at` | 200, `Schedule`; проверка стола через S2 |
| `GET /api/tables/{table_id}/availability` | Проверить свободный интервал | обязательные query `start_at`, `end_at` | 200, `Availability`; 404 без графика |
| `POST /api/holds` | Удержать интервал | `booking_id`, `table_id`, `start_at`, `end_at` | 201, `Hold`; 409 при занятости |
| `POST /api/holds/{hold_id}:confirm` | Закрепить удержание | `booking_id` | 200, `Hold`; 409 если срок истёк/чужая бронь |
| `DELETE /api/holds/{hold_id}` | Освободить интервал | обязательный query `booking_id`, тела нет | 200, `Hold`; 404/409 |

`Schedule`: `table_id`, `opens_at`, `closes_at`. Рабочее окно задаётся абсолютными
моментами времени; повторяющийся недельный календарь не моделируется. Закрытие должно
быть позже открытия, новый график не может вытеснить действующие удержания/брони.

`Hold`: `id` — UUID удержания; `booking_id` — его владелец; `table_id` — стол;
`start_at`, `end_at` — игровой интервал; `expires_at` — срок удержания;
`status` — `held`, `confirmed`, `released` или `expired`. Срок равен минимуму из
текущего времени +10 минут и начала игры. Повтор запроса удержания с тем же
`booking_id` и тем же активным интервалом возвращает существующее удержание.
Другие данные для этой же брони дают 409. Повторное закрепление уже закреплённого
интервала и повторное освобождение безопасны.

`Availability`: `table_id`, `start_at`, `end_at`, `available` (boolean) и
`busy_intervals` (`Hold[]` с пересечениями). `available=false` также получается для
прошедшего времени или интервала вне графика. Чтение доступности ничего не резервирует;
победитель при конкуренции определяется транзакцией `POST /api/holds`.

## S4. Бронирование

| Метод и путь | Назначение | Запрос | Ответ |
|---|---|---|---|
| `POST /api/bookings` | Создать бронь с ожиданием оплаты | `user_id`, `table_id`, `quote_id`, `start_at`, `end_at` | 201, `Booking`; проверки S1/S5/S3 |
| `GET /api/bookings` | Найти брони | query `user_id?`, `status?`, `offset`, `limit` | 200, `Booking[]` |
| `GET /api/bookings/{booking_id}` | Получить состояние и оплату | UUID брони | 200, `Booking`; 404 |
| `POST /api/bookings/{booking_id}:cancel` | Отменить до начала | UUID брони, тела нет | 200, `Booking`; 404/409 |

| Поле `Booking` | Тип и смысл |
|---|---|
| `id` | UUID брони |
| `user_id`, `table_id`, `quote_id`, `hold_id` | Ссылки на клиента, стол, предложение, удержание |
| `start_at`, `end_at` | Зафиксированный игровой интервал |
| `amount`, `currency` | Зафиксированная стоимость и `RUB` |
| `expires_at` | Срок оформления, полученный от S3 |
| `status` | `waiting_payment`, `confirmed`, `cancelled`, `expired`, `completed`, `no_show`; `rejected` зарезервирован для отклонённого состояния |
| `payment_id`, `payment_url` | До события `payment.created` равны null; затем реквизиты оплаты |
| `paid` | Получено ли событие успешной оплаты |
| `refund_status` | null, `pending`, `succeeded` или `failed` |
| `payment_attempts` | Список учтённых исходов неуспешной оплаты |
| `created_at` | Время создания |
| `cancelled_at` | Время отмены, до отмены null |

201 означает создание заявки и ожидание оплаты. Клиент повторяет GET, чтобы получить
созданный асинхронно платёж и итог подтверждения. S4 не принимает от клиента сумму:
она получается из проверенного предложения S5. После успешной оплаты S4 закрепляет
удержание в S3 и лишь затем меняет статус на `confirmed`.

Отмена повторяемая: уже отменённая бронь возвращается без второго события. Отмена
допускается до начала, при отмене оплаченной брони за два часа или более до начала запускается возврат.
Смена статуса оплаты, закрытие по сроку и завершение брони не имеют публичных ручных
эндпоинтов: ими управляют события. Поздняя оплата ранее неоплаченной закрытой брони вызывает полный возврат.

## S5. Тарифы и ценовые предложения

| Метод и путь | Назначение | Запрос | Ответ |
|---|---|---|---|
| `POST /api/tariffs` | Опубликовать новую версию | `game_type`, `hourly_rate` | 201, `Tariff` |
| `GET /api/tariffs` | Получить версии | query `game_type?`, `offset`, `limit` | 200, `Tariff[]` |
| `POST /api/quotes` | Рассчитать стоимость | `table_id`, `start_at`, `end_at` | 201, `Quote`; проверка S2 |
| `POST /api/quotes/{quote_id}:validate` | Проверить применимость | те же `table_id`, `start_at`, `end_at` | 200, сохранённый `Quote`; 404/409 |

`Tariff`: `id` — UUID версии; `game_type` — вид игры; `hourly_rate` — положительная
цена часа в копейках; `version` — последовательный номер версии для этого вида игры;
`currency` — `RUB`; `published_at` — время публикации. Изменение опубликованной версии
не предусмотрено: следующий POST создаёт новую, старые предложения сохраняют свою цену.

`Quote`: `id` — UUID предложения; `table_id`, `start_at`, `end_at` — применимость;
`amount`, `currency` — итоговая стоимость; `expires_at` — создание +10 минут;
`tariff_id`, `tariff_version`, `hourly_rate` — снимок использованного тарифа. Цена
считается как ставка × минуты /60 с округлением вверх до целой копейки.

S5 обращается в S2 за видом игры и публикацией стола. Это добавленная к итоговой
диаграмме проверка: вид игры не доверяется клиенту и у владельца S2/S5 появляется
обязательный межсервисный вызов из HTTP-эндпоинта. Нет тарифа/стол не опубликован — 409.
Проверка quote отклоняет другой стол, интервал и истёкший срок с 409; новая публикация
тарифа не изменяет ранее созданное действующее предложение.

## S6. Платежи

| Метод и путь | Назначение | Запрос | Ответ |
|---|---|---|---|
| `GET /api/payments` | Найти платежи | query `booking_id?`, `offset`, `limit` | 200, `Payment[]` |
| `GET /api/payments/{payment_id}` | Получить состояние | UUID платежа | 200, `Payment`; 404 |
| `POST /api/payments/{payment_id}:result` | Учебный результат оплаты | `status`, `amount`, `currency`; заголовок `X-Provider-Token` | 200, `Payment`; 401/404/409/422 |
| `POST /api/payments/{payment_id}:refund-result` | Учебный результат возврата | `status`; тот же заголовок | 200, `Payment`; 401/404/409/422 |

Платёж создаётся событием `booking.payment_requested`, запрос возврата —
`booking.refund_requested`. Поэтому HTTP POST для создания платежа и возврата нет.
`status` callback принимает `succeeded` или `failed`. В оплате `amount` обязателен,
положителен и совпадает со стоимостью платежа; `currency` по умолчанию `RUB`.

`Payment`: `id`, `booking_id`, `user_id`; `amount`, `currency`; `status` = `pending`,
`succeeded` или `failed`; `refund_status` = null/`pending`/`succeeded`/`failed`;
`refunded_amount` — фактически учтённый возврат в копейках; `created_at`;
`payment_url` — относительный путь callback в **S6**, не HTML-страница;
`provider` = `demo`; `refund_reason` содержит причину после запроса возврата, до него null.

Повтор успешного callback не создаёт второй переход или событие. Запоздалый отказ
после успеха не отменяет оплату. Результат возврата до запроса возврата даёт 409.
В учебной модели возвращается полная сумма, частичные возвраты не реализованы.

```http
POST http://localhost:8006/api/payments/{payment_id}:result
Content-Type: application/json
X-Provider-Token: demo-provider-token

{"status":"succeeded","amount":100000,"currency":"RUB"}
```

## S7. Игровые сеансы

| Метод и путь | Назначение | Запрос | Ответ |
|---|---|---|---|
| `GET /api/sessions` | Найти посещения | query `booking_id?`, `offset`, `limit` | 200, `Session[]` |
| `GET /api/sessions/{session_id}` | Получить посещение | UUID посещения | 200, `Session`; 404 |
| `POST /api/sessions/{session_id}:start` | Начать игру | UUID посещения, тела нет | 200, `Session`; проверка брони в S4; 404/409/503 |
| `POST /api/sessions/{session_id}:complete` | Завершить игру | UUID посещения, тела нет | 200, `Session`; 404/409 |

`Session`: `id`, `booking_id`, `user_id`, `table_id`, `start_at`, `end_at`;
`status` = `expected`, `active`, `completed`, `cancelled` или `no_show`;
`started_at`, `completed_at` — фактические времена, до соответствующего действия null.
Ожидаемое посещение создаётся событием `booking.confirmed`, максимум одно на бронь.

Старт разрешён при `start_at ≤ now < start_at + 15 минут` и актуальной подтверждённой
брони с совпадающими клиентом, столом и интервалом. При наступлении 15 минут таймер
фиксирует неявку. Повтор старта активного сеанса и завершения уже завершённого безопасен.
Завершение неначатого сеанса — 409. В конце интервала таймер завершает активный сеанс.

## S8. Уведомления

| Метод и путь | Назначение | Запрос | Ответ |
|---|---|---|---|
| `POST /api/notifications` | Подготовить сообщение | `user_id`, `message`; необязательные `booking_id`, `kind`, `scheduled_at` | 201, `Notification` |
| `GET /api/notifications` | Найти сообщения | query `user_id?`, `offset`, `limit` | 200, `Notification[]` |
| `GET /api/notifications/{notification_id}` | Получить состояние | UUID уведомления | 200, `Notification`; 404 |
| `POST /api/notifications/{notification_id}:send` | Выполнить попытку отправки | UUID уведомления, тела нет | 200, `Notification`; 404/409 |

`Notification`: `id`; `user_id`; `booking_id` (может быть null); `kind` = `custom`,
`confirmation`, `reminder` или `refund`, по умолчанию `custom`; `message` — непустой
текст 1–2000 символов; `scheduled_at` — время отправки, по умолчанию сейчас;
`status` = `prepared`, `sent`, `failed` или `cancelled`; `attempts` — число попыток;
`sent_at` — время успеха или null; `last_error` — последняя ошибка или null;
`provider` = `demo-log`.

Отправка получает актуальный контакт в S1. Учебный адаптер фиксирует доставку в логе;
внешнее сообщение клиенту не отправляется. Будущее `scheduled_at` даёт 409 при ручной
попытке раньше срока. Ошибка получения контакта записывается в объект; ответ 200 может
содержать `prepared` с отложенной следующей попыткой или `failed`. Следует читать
`status` и `last_error`, а не принимать код 200 за факт доставки. Уже отправленное,
отменённое или исчерпавшее попытки сообщение повторно не отправляется.

## Межсервисные вызовы и результат проектирования

| Вызывающий сервис | Вызываемый API | Причина |
|---|---|---|
| S3 | S2 `GET /api/tables/{table_id}` | Проверить существование и публикацию при настройке/удержании |
| S4 | S1 `GET /api/users/{user_id}` | Проверить клиента перед оформлением |
| S4 | S5 `POST /api/quotes/{quote_id}:validate` | Зафиксировать действующую цену выбранного интервала |
| S4 | S3 `POST /api/holds` | Атомарно занять время |
| S4 | S3 `POST /api/holds/{hold_id}:confirm` | После оплаты закрепить удержание |
| S5 | S2 `GET /api/tables/{table_id}` | Получить вид игры для расчёта цены; добавленная связь |
| S7 | S4 `GET /api/bookings/{booking_id}` | Проверить бронь перед стартом |

Итого описаны 33 бизнес-операции. `/docs`, `/openapi.json` и `/health` — технические
