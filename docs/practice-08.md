# Практическая работа 8. Тестирование микросервисов

## Цель и выбранные виды тестирования

Проверить восемь разработанных сервисов до развёртывания. Из трёх видов, предложенных
методичкой, выбраны **unit-тесты и компонентные тесты**. Все восемь сервисов имеют
проверки обоих видов. Интеграция с настоящими PostgreSQL/RabbitMQ дополнительно
проверяется smoke-сценарием, но не подменяет эти два набора.

## Изоляция и внедрение зависимостей

`Context` передаёт сервису репозиторий, HTTP-адаптер, часы и настройки. В unit-тестах
используется `MemoryStore`, HTTP заменён контролируемыми ответами, время задано явно.
Проверка истечения удержания не требует десятиминутного ожидания. Конкурентные вызовы
расписания запускаются через пул потоков: из 16 попыток удержать один интервал
успешной должна быть ровно одна.

В компонентных тестах `build_app(context=..., background=False)` создаёт одно FastAPI
приложение с его настоящими роутами и моделями. `TestClient` вызывает HTTP API;
проверяются коды ответа, тела, UUID, валидация, авторизация учебного callback и вызовы
внешних контрактов. Никакие пользовательские данные и внешние аккаунты не используются.

## Матрица проверок

| Сервис | Unit-тесты | Компонентные проверки |
|---|---|---|
| S1 Пользователь | Создание, уникальность контакта без учёта регистра, изменение | POST/GET/PATCH, 404/409/422, пустые и неверные поля |
| S2 Каталог | Уникальный номер, изменение и публикация | Создание/фильтрация/изменение, неподдерживаемый тип игры |
| S3 Расписание | Непересечение, конкурентные удержания, истечение и повторное закрепление | График, доступность, hold/confirm/release, вызов каталога |
| S4 Бронирование | Оплата, повтор события, отмена, граница возврата 120/119 минут, поздняя оплата, компенсации | Создание через S1/S5/S3, чтение и отмена, UUID и ошибки |
| S5 Тарифы | Версии, неизменность цены, точный срок quote, совпадение стола/интервала | Публикация тарифа, quote/validate, вызов каталога |
| S6 Платежи | Один платёж на бронь, совпадение суммы/валюты, повтор callback и возврат | Токен провайдера, исход оплаты/возврата, ошибки |
| S7 Сеансы | Единственное посещение, временное окно старта, неявка, автозавершение | Проверка брони через S4, старт/завершение, запрещённые переходы |
| S8 Уведомления | Дедупликация, отмена напоминания, три попытки, UTC-планирование | Создание/чтение/отправка, получение контакта через S1 |

Отдельно проверяются четыре варианта ПР5 и инфраструктура:

- расчёт задержек, уникальные варианты, имена очередей и настройки topology;
- откат бизнес-данных, inbox и outbox при неуспешной транзакции;
- повтор события с тем же UUID без повторного действия;
- некорректный JSON, UUID, конверт и заголовок попытки;
- направление повтора только собственному consumer;
- подтверждение публикации повтора/DLQ до ACK исходного сообщения;
- сохранение исходной неподтверждённой доставки и outbox при сбое публикации.

## Проверка связности восьми приложений

`tests/component/test_booking_flow.py` поднимает восемь ASGI-приложений в памяти.
Межсервисные запросы проходят через их HTTP-контракты. Доставка событий выполняется
тестовым диспетчером по настоящему списку bindings; каждое событие доставляется
повторно для проверки inbox. Проверяются четыре процесса:

1. Бронь → оплата → подтверждение → старт → раннее завершение без освобождения интервала.
2. Оплаченная бронь → отмена → возврат → отменённое посещение и напоминание.
3. Истечение удержания → поздняя оплата → полный возврат без восстановления брони.
4. Подтверждённая бронь → неявка → закрытие без автоматического возврата.

Это дополнительный тест контрактов и бизнес-процесса. Он не проверяет TCP, настоящий
AMQP, SQL-блокировки или контейнерную сеть.

## Воспроизведение

Из корня проекта после установки `requirements-dev.txt`:

```bash
python -m pytest tests/unit tests/component --cov --cov-report=term-missing
```

Для отдельного участника можно выбрать его два набора файлов, например для Андрея:

```bash
python -m pytest tests/unit/test_catalog.py tests/unit/test_pricing.py \
  tests/component/test_catalog.py tests/component/test_pricing.py
```

Проверка реального Compose-стенда:

```bash
docker compose up -d --build
python -m scripts.demo
python -m scripts.check_rabbitmq
```

`scripts.demo` проверяет HTTP-вызовы, PostgreSQL-сохранение и доставку событий через
RabbitMQ в процессе оформления/оплаты/отмены/возврата. `scripts.check_rabbitmq`
проверяет отправку и получение сообщений всех четырёх индивидуальных вариантов
в режимах `simple` и `variant`, включая фактическую задержку consumer и ручной ACK.

## Фактический результат

Результат финального прогона, метрики покрытия и статус контейнерного smoke-теста
зафиксированы в [validation.md](validation.md). Машиночитаемые результаты pytest
находятся в `reports/tests.xml`, текстовый вывод — `reports/tests.txt`.

Unit/component тесты не доказывают отсутствие всех ошибок. Нагрузочные испытания,
отказ хоста PostgreSQL, кластер RabbitMQ и долговременное восстановление саги
не входят в проверенный объём этой работы.

## Вывод

Тесты покрывают бизнес-правила всех восьми сервисов, их внешние HTTP-контракты и
критичные условия повторной доставки событий. Внедрение репозитория, HTTP-клиента
и часов позволяет проверять ошибки и пограничные моменты воспроизводимо.
