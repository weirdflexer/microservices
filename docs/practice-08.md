# Практическая работа 8. Тестирование микросервисов

## Цель и выбранные виды тестирования

Проверить бизнес-правила и HTTP-контракты всех восьми сервисов. Из трёх видов,
предложенных методичкой, выбраны **unit-тесты и компонентные тесты**. Наборы выполняются
в среде реализации: Python для S1/S2/S5/S8, Node.js для S3/S7, Go для S4/S6.
Дополнительно проверяется совместная работа всех языков с настоящими PostgreSQL
и RabbitMQ через публичный HTTP API.

## Изоляция и внедрение зависимостей

Unit-тесты вызывают бизнес-методы напрямую. Контекст передаёт хранилище, HTTP-адаптер,
часы и настройки. Вместо PostgreSQL используется MemoryStore, ответы зависимых
сервисов заданы явно. Управляемое время позволяет проверить десятиминутное удержание,
двухчасовую границу возврата и 15-минутную неявку без реального ожидания.
Node.js-тест расписания одновременно запускает 32 удержания одного интервала:
успешной должна быть ровно одна попытка.

Компонентные тесты проходят через настоящие роуты и валидацию одного приложения.
Python использует FastAPI TestClient с `background=False`. Node.js запускает свой
HTTP-сервер на свободном локальном порту и вызывает его через `fetch`. Go использует
`httptest.NewRequest` и `httptest.NewRecorder` со штатным `Handler`. Внешние HTTP-вызовы,
брокер и постоянное хранилище подменены; Docker и внешние аккаунты не требуются.

## Матрица проверок

| Сервис | Unit-тесты | Компонентные проверки |
|---|---|---|
| S1 Пользователь | Создание, уникальность контакта без учёта регистра, изменение | POST/GET/PATCH, 404/409/422, пустые и неверные поля |
| S2 Каталог | Уникальный номер, изменение и публикация | Создание/фильтрация/изменение, неподдерживаемый тип игры |
| S3 Расписание | Непересечение, конкурентные удержания, истечение и повторное закрепление | График, доступность, hold/confirm/release, вызов каталога |
| S4 Бронирование | Оплата, повтор события, отмена, граница возврата 120/119 минут, поздняя оплата, компенсации | Создание через S1/S5/S3, чтение и отмена, UUID и ошибки |
| S5 Тарифы | Версии, неизменность цены, точный срок quote, совпадение стола/интервала | Публикация тарифа, quote/validate, вызов каталога |
| S6 Платежи | Один платёж на бронь, совпадение суммы/валюты, повтор callback и возврат | Токен провайдера, исход оплаты/возврата, ошибки |
| S7 Сеансы | Единственное посещение, временное окно старта, неявка, автозавершение | Проверка брони через S4, старт/завершение, запрещённые переходы |
| S8 Уведомления | Дедупликация, отмена напоминания, три попытки, UTC-планирование | Создание/чтение/отправка, получение контакта через S1 |


Проверки каждого языка расположены рядом с соответствующим кодом:

| Набор | Файлы | Средства |
|---|---|---|
| Python S1/S2/S5/S8 и инфраструктура | `tests/unit/`, `tests/component/` | pytest, TestClient, управляемый Context |
| Node.js S3/S7 и инфраструктура | `services/schedule/tests/`, `services/sessions/tests/`, `common-node/tests/` | node:test, assert, локальный HTTP |
| Go S4/S6 и инфраструктура | `services/bookings/service_test.go`, `services/payments/service_test.go`, `internal/gokit/gokit_test.go` | testing, httptest, race detector |
| Совместная работа восьми сервисов | `tests/integration/` | pytest как независимый HTTP-клиент |

Проверяется откат бизнес-данных, inbox и outbox при ошибке, обработка дубликата без
повторного действия, некорректный JSON/UUID/конверт, ограничение повторов и DLQ.
Обработка сообщения требует подтверждённой публикации повтора или DLQ до ACK.
При сбое публикации исходная доставка остаётся неподтверждённой, а outbox сохраняется.
Python-набор также проверяет четыре профиля ПР5: задержки, имена очередей и топологию.

## Контрактные тесты реального стенда

`tests/integration/` не импортирует классы приложений или обработчики событий.
Тесты посылают HTTP/JSON-запросы в восемь работающих процессов на трёх языках;
межсервисные вызовы, SQL-транзакции и AMQP выполняются настоящими адаптерами.
При старте ожидаются `status=ok` и `broker_connected=true` у всех сервисов.

Проверяются оформление и подтверждение брони, посещение и уведомление, отмена,
освобождение интервала и полный возврат. Отдельные сценарии проверяют неудачную
оплату с последующим успехом, повтор callback, позднюю оплату ранее неоплаченной
брони и отсутствие возврата при обычной поздней отмене уже оплаченной брони.
Конкурентные HTTP-запросы проверяют единственного владельца интервала. Неверные UUID,
время, суммы, лишние поля и токен callback отклоняются без частичного изменения.

Сохранение данных проверяется в две фазы. Фаза `write` сохраняет снимки публичных
объектов всех восьми сервисов. Между фазами перезапускаются приложения и PostgreSQL
с сохранением томов. Фаза `verify` читает те же идентификаторы и сравнивает ответы;
она не создаёт данные заново. Команды и условия приведены в
[tests/integration/README.md](../tests/integration/README.md).

Реальные HTTP-тесты используют текущее время. Десятиминутное истечение, наступление
неявки и завершение по концу игры проверяются unit-тестами с управляемыми часами;
интеграционные тесты не ждут несколько часов. Каждый сценарий создаёт уникальные
учебные записи, базы при этом не очищаются.

## Воспроизведение

Локальные наборы из корня проекта:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest tests/unit tests/component --cov --cov-report=term-missing
npm --prefix common-node ci
npm --prefix common-node test
go test -race ./...
go vet ./...
```

Для Андрея можно выбрать Python-файлы каталога и тарифов:

```bash
python -m pytest tests/unit/test_catalog.py tests/unit/test_pricing.py \
  tests/component/test_catalog.py tests/component/test_pricing.py
```

Для Саши команда `npm --prefix common-node test` запускает оба сервиса и адаптеры.
Для Анвара unit- и HTTP-компонентные случаи можно выбрать отдельно:

```bash
go test ./services/bookings ./services/payments -skip '^TestHTTP'
go test ./services/bookings ./services/payments -run '^TestHTTP'
```

Проверка настоящего Compose-стенда:

```bash
docker compose up -d --build
RUN_HTTP_INTEGRATION=1 python -m pytest tests/integration \
  --ignore=tests/integration/test_http_persistence.py -q
python -m scripts.demo
python -m scripts.check_rabbitmq
```

`scripts.demo` показывает последовательный процесс оплаты, отмены и возврата.
`scripts.check_rabbitmq` проверяет все четыре индивидуальных профиля ПР5 в режимах
`simple` и `variant`, включая фактическую задержку consumer и ручной ACK.

## Фактический результат

Прогон 7 ноября 2026 г.: **91 Python-тест** (86 unit и 5 component),
**75 Node.js-тестов** и **35 Go-тестов верхнего уровня** завершились успешно.
Дополнительно прошли 42 HTTP-проверки реального стенда, демонстрация оплаты и возврата,
все 8 вариантов RabbitMQ и чтение восьми контрольных объектов после полного
пересоздания контейнеров с сохранёнными томами. Старые записи Python также доступны
через новые S3/S4/S6/S7. `go test -race` и `go vet` не обнаружили проблем.

Покрытие Python — 78,9% строк; Node.js — 90,38% строк; Go — 87,3% statements
для bookings, 86,9% для payments и 42,4% для gokit. Проценты инструментов не
объединяются. Команды, область измерения и журналы приведены в
[validation.md](validation.md).

Unit/component тесты не доказывают отсутствие всех ошибок. Нагрузочные испытания,
отказ хоста PostgreSQL, кластер RabbitMQ и долговременное восстановление саги
не входят в проверенный объём этой работы.

## Вывод

Каждый участник имеет unit- и компонентные проверки своих сервисов на выбранном
языке. Дополнительные HTTP-тесты проверяют совместимость Python, Node.js и Go через
общие контракты и фактическую доставку событий. Проверка после перезапуска отдельно
подтверждает чтение сохранённых объектов всех восьми сервисов.
